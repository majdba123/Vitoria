# Backup and Restore

Stakeholder requirement: "أرشفة المعلومات – احتياطي المعلومات – كيف؟" (data
archiving — data backup — how?). This document covers **backup** (recoverable
copies of data/files after loss or corruption). See
[`docs/architecture/DATA_RETENTION_AND_ARCHIVING.md`](../architecture/DATA_RETENTION_AND_ARCHIVING.md)
for **archiving** (keeping historical records available but out of active
operational views) — the two are deliberately not mixed.

## Implementation

Backups run through [`spatie/laravel-backup`](https://spatie.be/docs/laravel-backup)
(`config/backup.php`), scheduled from `routes/console.php`. This was chosen
over a bespoke script because the required capabilities — DB dump, file
archive, retention/cleanup, health monitoring, and failure notifications — are
exactly what it does out of the box, tested against MySQL/PostgreSQL/SQLite,
with no code to maintain beyond configuration.

### What is backed up

- **Database**: the connection named by `DB_CONNECTION` (MySQL in production,
  SQLite in local/dev), dumped and gzip-compressed.
- **Private uploads** (`storage/app/private`): vendor compliance documents and
  commercial registers (`app/Models/VendorDocument.php`).
- **Public uploads** (`storage/app/public`): product photos and other
  user-uploaded media. This directory is entirely git-ignored
  (`storage/app/public/.gitignore`), so it only exists in the backup, not in
  version control.
- **`.env`**: needed to reconstruct the environment on a fresh host after a
  full loss. It never leaves the `backups` disk (see "Security" below).

### What is NOT backed up

Excluded via `backup.backup.source.files.exclude` in `config/backup.php`:

- `vendor/`, `node_modules/` — regenerated by `composer install` / `npm ci`.
- `.git/` — the repository itself is the source of truth for code; deployment
  pulls from git, it does not restore from a backup archive.
- `public/build/`, `bootstrap/cache/` — regenerated by `npm run build` /
  `artisan optimize`.
- `storage/framework/`, `storage/logs/`, `storage/pail/` — framework runtime
  state and logs, not business data.
- `storage/app/tmp/`, `storage/app/backup-temp/` — transient working
  directories (mPDF render cache, the backup tool's own staging area).
- `storage/app/backups/` itself — never back up the backup destination.
- Database *queue* and *session* tables are included in the dump (they're
  ordinary tables), but their content is disposable by design; a restore does
  not need to preserve in-flight jobs or sessions to be correct.

### Frequency and retention

Configured in `routes/console.php` and `config/backup.php`:

| Command | Schedule | Purpose |
|---|---|---|
| `backup:run` | daily at 01:30 | creates the DB dump + file archive |
| `backup:clean` | daily at 02:30 | enforces retention (below) |
| `backup:monitor` | daily at 03:00 | fails loudly if the newest backup is missing/stale/oversized |

Retention (`config/backup.php` → `cleanup.default_strategy`, Spatie's
`DefaultStrategy`):

- All backups kept for 7 days.
- Then one per day kept for 16 days.
- Then one per week kept for 8 weeks.
- Then one per month kept for 4 months.
- Then one per year kept for 2 years.
- Oldest backups are pruned first if total storage exceeds 5,000 MB.

This is separate from the **pre-deploy** snapshot already taken by
`.github/workflows/deploy.yml` (a one-off `mysqldump` before each release, at
`storage/backups/pre-deploy-*.sql.gz`) — that snapshot exists to make a single
deployment revertible and is not a substitute for the recurring schedule
above; the two do not overwrite or interfere with each other (different
directories: `storage/app/backups/` vs `storage/backups/`).

### Storage destination

Backups are written to the `backups` disk (`config/filesystems.php`), rooted
at `storage/app/backups/`. This is a plain local disk in the current
deployment; because Spatie's backup destination is disk-based, pointing it at
an S3-compatible bucket instead is a configuration change (add credentials,
change `destination.disks` to `['s3']`), not a code change — see
"Production infrastructure requirements" below for what that would need.

### Encryption

Archive encryption is controlled by `BACKUP_ARCHIVE_PASSWORD` (`.env`). When
set, `config/backup.php` enables AES-256 zip encryption
(`'encryption' => 'default'`). Leave it unset in local/dev; **set it in
production** so a stolen/leaked backup file is not directly readable. Never
commit the password — it lives only in the production `.env`.

## Security

- The `backups` filesystem disk has `'visibility' => 'private'` and no `url`
  key, and its root (`storage/app/backups`) is outside both `public/` and
  `storage/app/public/` — it is never reachable through the `public/storage`
  symlink or any route. Verified by
  `tests/Feature/BackupConfigurationTest.php`.
- There is no admin endpoint that serves a backup file or DB dump over HTTP.
  Downloading a backup is an operator action on the server (see "How to
  verify a backup" below), not an application feature — this was a deliberate
  choice: exposing dumps through the app would turn a backup mechanism into a
  new attack surface.
- `.env` inside the archive contains production secrets; treat the archive
  itself as sensitive and restrict filesystem/SSH access to the backup
  directory (or the S3 bucket, if configured) the same way you would restrict
  access to `.env` on the live server.

## How to manually trigger a backup

```bash
php artisan backup:run
```

Flags worth knowing:

```bash
php artisan backup:run --only-db      # database dump only
php artisan backup:run --only-files   # file archive only, skips the DB dump
```

## How to verify a backup

```bash
php artisan backup:list
```

Prints every stored backup with its size, date, and reachability. To confirm
health against the configured thresholds (age, total size):

```bash
php artisan backup:monitor
```

To inspect an archive's contents without extracting it:

```bash
unzip -l storage/app/backups/<AppName>/<timestamp>.zip
```

## Database restore

1. Put the application in maintenance mode: `php artisan down`.
2. Locate the backup: `php artisan backup:list`, or find the `.sql.gz` inside
   the extracted zip under `db-dumps/`.
3. Extract the zip and decompress the dump:
   ```bash
   unzip storage/app/backups/<AppName>/<timestamp>.zip -d /tmp/restore
   gunzip /tmp/restore/db-dumps/<connection>.sql.gz
   ```
4. Restore into MySQL (production):
   ```bash
   mysql -u "$DB_USERNAME" -p"$DB_PASSWORD" -h "$DB_HOST" "$DB_DATABASE" < /tmp/restore/db-dumps/<connection>.sql
   ```
   Or, for a local/dev SQLite restore, copy the extracted `.sql` back into the
   database file with `sqlite3 database/database.sqlite < <connection>.sql`
   after recreating an empty database file.
5. Run `php artisan migrate --force` only if the restored dump predates
   migrations that have since shipped — check `migrations` table first;
   restoring a dump that already has your latest migration rows is normal and
   needs no further migration.
6. Rebuild caches and bring the app back up:
   ```bash
   php artisan optimize:clear
   php artisan config:cache
   php artisan route:cache
   php artisan up
   ```
7. Smoke-test login, cart, checkout, ledger, and settlement reads before
   reopening traffic to the public — the same checklist already used for
   deployment rollback in
   [`docs/deployment/PRODUCTION_READINESS.md`](../deployment/PRODUCTION_READINESS.md).

## File restore

1. Extract the zip: `unzip storage/app/backups/<AppName>/<timestamp>.zip -d /tmp/restore`.
2. The archive preserves the original absolute-minus-`base_path()` structure
   under the include paths, so restored files land at, e.g.,
   `/tmp/restore/storage/app/private/vendor-documents/...`.
3. Copy the needed subtree back into place:
   ```bash
   cp -r /tmp/restore/storage/app/private/vendor-documents storage/app/private/
   ```
4. If restoring `storage/app/public`, re-run `php artisan storage:link` only
   if the symlink itself was lost (the link target doesn't change).
5. Verify file ownership/permissions match the web server user before
   resuming traffic — a restore that leaves files owned by the deploying user
   instead of the web server user will 403 on the next request.

## Rollback considerations

- A database restore is a point-in-time rollback: any order, payment, or
  ledger entry created after the backup's timestamp is lost. Cross-check the
  restored `orders`/`vendor_ledger_entries` max `created_at` against
  payment-provider records before declaring a restore complete — this is a
  business reconciliation step, not something a script can safely automate.
- Restoring only the database without restoring files (or vice versa) can
  leave dangling references (e.g., an order pointing at a since-deleted
  invoice PDF path, or a vendor document row with no file back of it).
  Restore both from the *same* backup timestamp unless you have a specific
  reason not to.

## Production infrastructure requirements

- **Cron / scheduler**: Laravel's `Schedule::` entries in `routes/console.php`
  do nothing on their own — they only run when something calls
  `php artisan schedule:run` every minute. Production already requires this
  (`docs/deployment/PRODUCTION_READINESS.md` documents the same cron line for
  the existing discount-expiry commands):
  ```cron
  * * * * * cd /var/www/MSZ && php artisan schedule:run >> /dev/null 2>&1
  ```
  No new cron entry is needed — `backup:run`/`backup:clean`/`backup:monitor`
  ride on the same `schedule:run` tick as everything else.
- **`mysqldump` on PATH**: required for the MySQL dumper to run in production
  (the deploy workflow already asserts this for the pre-deploy snapshot, so
  production hosts already satisfy it).
- **`BACKUP_ARCHIVE_PASSWORD`**: must be set in the production `.env` to get
  encrypted archives (see "Encryption" above). Not set = unencrypted backups.
- **`BACKUP_NOTIFICATION_EMAIL`** and a working `MAIL_MAILER`: required for
  `BackupHasFailedNotification` / `UnhealthyBackupWasFoundNotification` /
  `CleanupHasFailedNotification` to actually reach a human. Locally
  `MAIL_MAILER=log` just writes to the log file, which is why failures are
  *also* written to `storage/logs/laravel.log` via `Log::error()` in
  `routes/console.php` regardless of whether mail is configured — see
  "Disaster recovery checklist" below for why this matters.
- **Off-site storage (optional, recommended)**: the `backups` disk is local by
  default. A host failure that takes down the disk takes the backups with it.
  Pointing `destination.disks` in `config/backup.php` at `['backups', 's3']`
  (after configuring the existing `s3` disk in `config/filesystems.php` with
  real credentials) makes Spatie copy every backup to both. This was left as
  an infrastructure decision rather than hardcoded, since it depends on
  whether/which object storage the hosting provider offers.

## Disaster recovery checklist

1. Confirm the scope of loss (DB only, files only, both, or full host loss).
2. `php artisan down` if the app is still reachable.
3. Identify the most recent healthy backup: `php artisan backup:list` /
   `php artisan backup:monitor`.
4. Restore database (see above), then files (see above), from the *same*
   backup timestamp.
5. Reconcile: compare restored order/payment/ledger timestamps against any
   external payment-provider or shipping-provider records for the gap between
   the backup and the incident.
6. Rebuild caches, run migrations only if needed, `php artisan up`.
7. Smoke-test the critical paths listed under "Database restore" step 7.
8. Write an incident note: what was lost (the gap between last backup and
   incident), root cause, and whether the backup frequency (currently daily)
   is still adequate for the business's tolerance for data loss.
