# Stakeholder Review Resolution Matrix

This document tracks the resolution of every item in the handwritten stakeholder review against the Vetora marketplace (Laravel 12 + Inertia + React 19 + Tailwind 4). Phase 1 was a full evidence-gathering pass across the codebase before any change was made, so several items below were found to already be fixed by newer approved work, or obsolete against the current architecture.

Full test suite: **337 passed (1820 assertions)**. Production build: **passing**. Laravel Pint (`vendor/bin/pint --test`): **passing**.

## Final Acceptance Audit (second pass, no new features)

A follow-up closure pass addressed five gaps flagged in review of the first pass: real automated accessibility scanning, a fuller browser QA matrix, visual re-verification of the Hero, adversarial (negative-path) security tests for the new RBAC surface, and a definitive dependency audit of the legacy Blade tree.

**Bug found and fixed during this pass (reported live by the user):** a category page's product count showed "0 products" while the product listing directly below it rendered a real product. Root cause: `Api\Admin\CategoryController::show()` never computed `products_count` at all (`Category::toArray()` has no such attribute), so the frontend's `category.products_count || 0` always fell back to 0. Fixed by adding a `loadCount(['products as products_count' => fn($q) => $q->visible()])` (matching exactly what the product listing below actually shows), and extending `ProductService::flushProductCache()` to also flush the `categories` cache tag so approving/adding a product updates the count immediately rather than after the cache TTL. Regression tests: `tests/Feature/CategoryProductsCountTest.php` (3 tests, including one that proves the cache invalidates live).

1. **Adversarial RBAC/security tests** (`tests/Feature/AdversarialSecurityAuditTest.php`, 11 new tests) — proved as hard 403s, not silent no-ops: an employee without `products.moderate` approving a product; a vendor approving their own product; vendor A editing/deleting vendor B's product; an employee without `orders.view` viewing a specific order; an admin assigning a vendor-scoped role (owner/manager) to an employee; assigning roles to a non-employee account; a non-admin/self-assigning employee calling the role-assignment endpoint; unauthenticated requests to every sensitive endpoint. **This surfaced and fixed a real gap**: a vendor sending `status` on their own product update returned 200 (silently ignored) rather than a hard 403 — `VendorUpdateProductRequest` doesn't even declare `status` as a validation rule, so it never reached the existing strip-logic at all. `ProductController::update()` now checks the raw request (`$request->has('status')`) instead of only the validated array, and aborts 403 for any unauthorized status-change attempt, vendor or employee.
2. **Full browser QA matrix** — logged into and verified (via real login, not just static review) all four role dashboards (Admin, Vendor, Employee, Syndicate), Register, Categories index, dark mode, and 768/1024/1440 breakpoints, on top of the pages already covered in the first pass. No horizontal overflow, no console errors, all real data.
3. **Hero re-verification** — measured directly (not just visually judged): 99.3% viewport width, 700px height at 1440×900, zero gap above (header) or below (next section), confirming genuinely full-bleed cinematic framing with no dead space.
4. **Legacy Blade dependency audit** — a dedicated Explore agent proved 68 of 69 legacy Blade files (`resources/views/admin/**`, `vendor/**`, `employee/**`, `syndicate/**`, `products/**`, `categories/**`, `auth/**`, `checkout/**`, `orders/**`, `preferences/**`, `vendors/**`, `profile.blade.php`) had zero live references — every route uses `Inertia::render`. The one exception, `resources/views/errors/403-vendor.blade.php`, was rendered by `EnsureUserIsVendor`/`EnsureUserIsSyndicate` middleware for non-JSON requests. Both middleware were changed to `redirect()->route('login')` (matching the existing `EnsureUserIsAdmin`/`EnsureUserIsEmployee` pattern), and the entire 69-file tree was deleted.
5. **Real automated accessibility scanning** — AccessLint's `audit_live`/`audit_html` tools failed with a CDP integration error in this environment (`CDP error: Unexpected token 'v', "var Access"...`, an environment/tooling issue, not fixable from the app side). Got a genuine automated scanner working instead via Playwright's browser (which has outbound network access) injecting **axe-core 4.9.1** from a CDN and running `axe.run()` against the live DOM — a real, industry-standard WCAG rule engine, not a manual review. Swept Home, FAQ, Product Details, Vendor storefront, Categories, product-type select, Login, Register, and all four dashboards; fixed every violation found and re-scanned to zero:
   - **Serious — color contrast**: Home's "01/02" type-selector numbers (1.56:1 → fixed to ~3.3:1), Vendor sidebar's empty-categories message (3.6:1 → fixed), Employee/Syndicate sidebar Sign Out button (1.68:1 — root cause: a light/dark-mode-swapping color token used on a sidebar surface that's always dark regardless of site theme, so in light mode it resolved to a dark-on-dark color; fixed by using the fixed dark-surface-safe token), Employee/Vendor/Syndicate sidebar "workspace" labels (2.89:1 → fixed).
   - **Critical — missing accessible name**: the Register page's City `<select>` (Radix combobox button) had no discernible name to assistive tech — `<label for>` association isn't reliably honored for ARIA-role buttons. Fixed once in the shared `SelectField` component (`aria-label={label}`), which applies to every select field across the whole app, not just Register.
   - **Moderate — landmark structure**: every workspace layout (Admin/Vendor/Employee/Syndicate) nested a second `<main>` inside shadcn's `SidebarInset` (which already renders one) — fixed by changing the inner wrapper to a `<div>` in all four `Layouts/*.jsx`. The sidebar navigation itself had no landmark role at all (~20 nodes of nav content unreachable via landmark navigation) — fixed by adding `role="navigation"` + a descriptive `aria-label` to all four `*Sidebar.jsx` components.
   - **Moderate — heading order**: the Footer's "Shop/Account/Contact" group headings were `<h3>` with no preceding `<h2>` on pages like the new FAQ page — promoted to `<h2>`. Employee Dashboard had a stray `<h3>` tile label that wasn't a real section heading (inconsistent with every other card title on the same page, which use a non-heading `CardTitle` `<div>`) — changed to `<p>`. Syndicate Dashboard's `InsightPanel` titles (`<h3>`) had no `<h2>` ancestor on the Overview tab — added a visually-hidden (`sr-only`) `<h2>`.

## Financial closure round (this pass)

`585aaa4` was the first push after the Pint linter had never been run locally in this session; `vendor/bin/pint --test` revealed 3 consecutive CI failures (Pint style violations, not test failures) that had gone unnoticed because only `php artisan test` had been checked before pushing. Fixed and confirmed passing before continuing. This is recorded here because it is exactly the kind of "claimed done, not independently verified" gap this round was asked to close.

This round closed five specific financial/data-integrity edge cases, all financial money-path items — no new features:

1. **Concurrent settlement race**: `VendorLedgerService::recordSettlement()` previously read `outstanding` *before* opening its `DB::transaction()`, so two concurrent settlement requests for the same vendor could each read the same stale balance and together settle more than was ever owed. Fixed by moving the read inside the transaction, against a `lockForUpdate()`-locked vendor row, so a second concurrent call blocks until the first commits and then recomputes against the true post-settlement balance. New test: `two settlement requests racing off the same stale outstanding balance can never together exceed it` (`tests/Feature/VendorCommissionLedgerReconciliationTest.php`), which reproduces the exact stale-read scenario the old code was vulnerable to via the real `/api/admin/vendors/{vendor}/settlements` HTTP endpoint.
2. **Backfill command hardening**: `ledger:backfill-completed-orders` cannot know the commission rate that was actually in effect when a legacy order completed (no historical rate is stored anywhere in the schema) — it can only use each category's *current* rate. This is a real, undocumented accuracy limit, not a bug that can be silently fixed. The command's docblock and `--dry-run` output now say so explicitly, `--dry-run` now shows the computed amount per order (not just the order id) so an operator can sanity-check for rate drift before committing, and a real write requires `ConfirmableTrait`'s confirmation (auto-skipped outside `production`, exactly like `migrate`). New test proves `--dry-run` against a database with a legacy order under a since-changed commission rate writes nothing.
3. **Commission dashboard semantics unified**: both commission-stats endpoints previously returned a field named `completed_order_total` that actually summed CONFIRMED + COMPLETED orders (a live/projected preview), sitting in the same `financials` object as `commission_total`/`paid_amount`/`remaining_amount` (ledger-authoritative, COMPLETED-only, snapshotted at completion). Renamed to `projected_order_total` (and `completed_orders_last_7_days` → `recent_orders_last_7_days`), and added an explicit `basis` field in the response listing exactly which keys are `ledger` vs `projected` so no consumer has to infer it from naming. Also removed the unused `vendor_net_total` field, which mixed a projected figure with a ledger figure. Also fixed the Admin paid-amount screen's confirmation dialog, which warned against exceeding `commission_total` (the platform's cut — an unrelated number) instead of the actual cap the ledger enforces (`remaining_amount`/outstanding). New test: `the commission dashboard response explicitly separates ledger-authoritative figures from the projected preview`.
4. **Invoices duplicate preflight**: `2026_08_20_100000_add_unique_order_id_to_invoices_table` now queries for existing duplicate `order_id` rows before applying `unique('order_id')`, and throws a `RuntimeException` naming the affected order_id(s) instead of letting a raw DB integrity-constraint violation abort the migration mid-way. It does not delete or merge data itself — reconciling which duplicate invoice is authoritative is a business decision. Two new tests in `tests/Feature/InvoiceDuplicatePreflightMigrationTest.php` prove it blocks against a database seeded with a real duplicate, and applies cleanly when there is none.
5. **Concurrency test**: see item 1 above — the same test satisfies both the settlement-race fix and this requirement.

**Evidence for this round** (all commands actually executed, not asserted): `php artisan test --compact` → **336 passed (1814 assertions)**; `npm run build` → succeeded, no errors; `vendor/bin/pint --test` → `{"result":"pass"}`; `php artisan migrate:fresh --seed --force` against the local `sqlite` database → every migration including the new preflight-checked one applied cleanly (`DONE`), full demo seed data loaded without error.

**Still open at that point:** #10 (full responsive matrix) and #18/19/23 (Employee/Syndicate trend charts) — both explicitly deprioritized to after this financial-closure round, per the requester's own stated order ("money first → migration safety → doc consistency → Employee/Syndicate charts").
